# Build Phase-Aware Execute Opportunity 否决记录

## 本地取证文件

- `l2_swimlane_records.json`：B256、real-compute `6,28,4,1` 的原始泳道。
- `merged_swimlane.json`：由上述 raw 转换的 Perfetto 泳道。

两份 JSON 体积较大，只保留在本机该目录供复查，不纳入 Git 提交；本文保存
冻结 A/B、泳道汇总和否决原因。

## 方案

每个 Build 在完成 Register 并发布本 task 的 TensorMap insert completion 后、
进入 Fanin 和发布 BUILT 前，检查一次本核已经持有的四个 Execute token。机会点
不领取新 Execute ticket，只选择 task id 最小的一个 token，最多推进一个。

## trace-free 冻结 A/B

6 对 B-C/C-B 反转交错结果：

```text
基线中位数 = 1011.904 us
候选中位数 = 1035.376 us
候选回退   = 23.473 us / 2.320%
候选获胜   = 0 / 6 对
配对差中位 = +24.178 us
```

候选虽把 208 个 kernel 移到 Build opportunity，但 FinalDrain 仍为 122；与撤回后
典型的 `EfDrain=902, FinalDrain=122` 对照，这 208 个任务主要来自原本下一次
EfDrain 就会推进的工作，而不是消减尾部。与此同时，全部 1,280 个 Build 都要
支付第二次 split Finish、continuation 校验和四 token 扫描，只有 16.25% 的
机会实际完成 kernel。同步执行旧 task 还会延后当前 task 的 Fanin/BUILT，降低
后续 ready payload 的生成速度。固定成本大于局部提前收益，因此端到端稳定回退。

## 泳道加工说明

候选允许 Kernel 位于 Register 与 Fanin/AllocComplete 之间，正式 sparse
validator 和 exclusive analyzer 的现行状态机不接受这种已否决结构。设备原始
结果通过全部语义断言后，本记录只用临时 host exporter 将相邻端点要求从
“时间戳严格相等”放宽为“时间区间不得重叠”，导出 raw 并生成 Perfetto 合并
泳道；临时 exporter 修改未进入设备代码且已撤回。exclusive analysis 未生成，
不能把缺失该文件误解为设备正确性失败。
