# 2026-08-06 Register 等待执行检查点否决记录

## 本地取证文件

- `register_wait_exec_k16_rejected.json`

这是 B256、real-compute `6,28,4,1`、full-swimlane 的合并泳道图。候选在
严格 Register 前序等待中，每 16 次 pending load 轮转检查一个 owner-local
Execute token；不领取新 Execute ticket，kernel 开始后同步执行到底。

该 JSON 体积较大，只保留在本机 `test_record/2026-8-6/` 供复查，不纳入
Git 提交；本文保存可长期评审的测试口径、关键数据和否决结论。

## 正确性

本轮设备结果全部通过：1,280 个 Build、1,024 个 kernel、严格 TensorMap
插入、payload、fanin、DCCI、completion、FinalDrain 和 exactly-once 均闭合。
因此否决原因是性能模型错误，不是功能未跑通。

同窗修改前的单次 trace-free 基线为 `996.663 µs`。此前
`cross_waitbuilt_1p084ms.json` 中前序等待 load 数量中位为 20，对应等待区间

候选代码撤回并重新编译后，B256 trace-free 端到端为 `979.943 µs`，所有
正确性与语义断言通过，kernel placement 为 `EfDrain=902, RingBp=0,
FinalDrain=122`。这说明性能已回到约 1 ms 基线，回退可明确归因于候选结构。

## 结论

检查点达成了局部目标：首个 AIC kernel 明显提前。但 QK/SF/PV 的同步 kernel
约为 28--54 µs，而触发检查点后的剩余前序等待通常远短于 kernel。执行期间
一旦 predecessor 已发布，当前 Build 仍不能继续 Register；延迟随后沿严格
task-id 插入链传递。结果是 826 个必要 kernel 被大量串入全局顺序链，端到端
约扩大到基线的三倍。

因此，**在严格 Register 等待内同步执行完整 kernel 的方案正式否决并从生产
代码撤回**。固定轮询阈值无法预测“当前等待还剩多久”；继续枚举 32/64/128
只会在“更多链路阻塞”和“逐渐退化为完全不触发”之间移动，不能修复结构性
矛盾。

现有排他分析器会拒绝这份候选 raw，报出 Kernel 没有 EfDrain 或 winner-tail
父区间。这是因为候选新增了 Register 内 kernel，而当前分析合同故意不允许
该结构。合并泳道已经成功生成，可直接用 Perfetto 查看；既然生产方案已否决，
不扩张正式 analyzer 去兼容这一过程态。
