# Atomic 不同地址的 bank 冲突验证

## 要回答的问题

已有同址测试表明，多 Scalar 同时对同一地址执行 atomic 时近似满足 `T(N)=A+B×N`，其中
`B≈170ns/Scalar`。本用例继续验证两个问题：

1. 两个 Core 访问不同的 64B Scalar cache line，但地址位于同一个 512B 区间时，是否仍会完整串行一个 `B`；
2. 多个 Core 各自访问独立地址时，地址布局会造成多大的实际排队损失；
3. 实际的 N 个 Core 分成两个同址热点组时，两组是合并成 `B×(nA+nB)`，还是并行成
   `B×max(nA,nB)`。

## 实测结论

**“同一 512B 区间内的不同 64B 行共用一条 `B≈170ns` 队列”不成立；但只给 AIC/AIV cursor
各自独占 64B 仍不安全，设备表现出稳定的 128B 冲突粒度。**

针对实际的两组热点场景，结论更直接：

- 两个热点地址位于同一个对齐 128B 区间时，两组会合并排队，曲线是 `A+B×(nA+nB)`；
- 两个热点地址跨过 128B 边界后，两组可以并行，整体完成时间是 `A+B×max(nA,nB)`；
- 相隔 128B、512B、1024B 都符合后一种形态，没有观察到“相隔 512B 仍共享一条 B 队列”。

## N 个 Core 分成两个同址热点组

纯 AIC、纯 AIV 将 N 个 Core 近似对半分组；混合场景按 AIC→组 A、AIV→组 B。组内所有 Core
访问同一地址，两个组分别访问地址 A/B。布局覆盖：

- A/B 为同一地址，作为 `B×N` 对照；
- A/B 相隔 64B，分别让两地址处于同一个 128B 区间和跨越 128B 边界；
- A/B 相隔 128B、512B、1024B。

下表中，“同 128B”按总核数 N 拟合 B，“跨 128B”及更大间距按较大组人数 `max(nA,nB)` 拟合 B。
如果对应模型成立，这些 B 都应接近同址对照的约 170ns。

| 场景 | 同址 B/ns | 64B 同 128B：B/总核数 | 64B 跨 128B：B/最大组 | 128B：B/最大组 | 512B：B/最大组 | 1024B：B/最大组 |
|---|---:|---:|---:|---:|---:|---:|
| 纯 AIC | 170.45 | 170.42 | 174.62 | 174.65 | 169.53 | 171.26 |
| 纯 AIV | 172.78 | 172.80 | 175.59 | 175.61 | 170.02 | 171.27 |
| AIC+AIV 混合 | 173.42 | 173.49 | 175.33 | 175.26 | 173.23 | 173.39 |

纯 AIC/AIV 的两组近似等大，`N` 与 `max(nA,nB)` 只是固定的二倍关系，单看 R² 无法区分两个模型。
混合场景的 AIC/AIV 人数比例随 N 的取整变化，是更有区分力的证据：

| 混合场景布局 | 按总核数拟合 R² / RMSE | 按最大组拟合 R² / RMSE | 更符合的模型 |
|---|---:|---:|---|
| 64B、同一 128B 区间 | 0.999957 / 17.62ns | 0.999559 / 56.41ns | `nA+nB` |
| 64B、跨 128B 边界 | 0.999581 / 37.65ns | 0.999929 / 15.50ns | `max(nA,nB)` |
| 相隔 128B | 0.999588 / 37.31ns | 0.999933 / 15.08ns | `max(nA,nB)` |
| 相隔 512B | 0.999600 / 36.31ns | 0.999894 / 18.69ns | `max(nA,nB)` |
| 相隔 1024B | 0.999591 / 36.79ns | 0.999941 / 14.00ns | `max(nA,nB)` |

也就是说，每个热点组内部仍以约 170ns/次串行；只要两个热点地址位于不同的对齐 128B 冲突单元，
两条组内队列可以重叠执行，总时间主要由人数更多的组决定。

双 Core 的归一化串行比例如下。比例接近 1 表示额外耗时与同址排队相同，接近 0 表示两次 atomic
基本并行。

| 场景 | 间距 64B | 间距 128B | 间距 512B |
|---|---:|---:|---:|
| 纯 AIC | 1.000 | 0.045 | -0.068 |
| 纯 AIV | 1.000 | 0.012 | 0.006 |
| AIC+AIV 混合 | 1.000 | 0.012 | 0.006 |

固定 `gap=64B` 还不足以区分“64B 间距总会冲突”和“存在更大的对齐粒度”，因此又将地址对的起点逐 64B
平移：

- `+0/+128/+256/+384B` 起点：两地址处在同一个 128B 区间，三类核的串行比例均为 1.000；
- `+64/+192/+320/+448B` 起点：两地址跨 128B 边界，三类核的串行比例为 0.012–0.046。

因此，64B 相邻地址的冲突严格随 128B 边界交替，不是固定基址上的偶然单点。

## 对 cursor 布局的直接含义

若目标是保证 AIC cursor 与 AIV cursor 不因这个粒度互相排队，不能只声明两个独立的 64B 对象并让它们
自然相邻。当前设备实测支持的保守布局是：

- 每个 cursor 使用独立的 128B 槽；
- 槽的首地址按 128B 对齐；
- 不把“两个对象各自大小为 64B”等同于“它们位于不同冲突单元”。

这里的 128B 是当前设备、DIE0 Core → GM0、当前 atomic 类型下的实测冲突粒度，不写成未经文档证明的
通用硬件接口保证。

## 多 Core 独立地址结果

最大并发点的全局完成跨度中位数如下：

| 场景 | 最大 N | 同址/ns | 64B 步长/ns | 128B 步长/ns | 512B 步长/ns | 1024B 步长/ns |
|---|---:|---:|---:|---:|---:|---:|
| 纯 AIC | 16 | 2778.0 | 503.0 | 306.0 | 306.0 | 227.0 |
| 纯 AIV | 32 | 5589.0 | 514.2 | 315.0 | 318.0 | 238.8 |
| AIC+AIV 混合 | 48 | 8362.2 | 522.8 | 325.0 | 321.8 | 254.0 |

64B 步长确实有损失：相邻两条 64B 行会成对排队。不过，不同的 128B 组仍能并行，所以它不是整个
512B 区间、也不是全部 N 个 Core 串成一条 `170ns×N` 队列。以 48 Core 混合场景为例，64B 步长为
522.8ns，而 1024B 步长为 254.0ns。

不同地址曲线不再服从单条 `A+B×N`：多个步长的低 N 线性拟合 R² 很低，说明其形态是多个冲突组并行、
组内串行以及地址自身固定延时共同作用的结果，不能把拟合斜率继续解释为同址 HA 的 `B`。

## 为什么 512B 单点容易误判

`base+512B` 的双 Core 绝对跨度约为 290–304ns；对应的两次单核并行基线约为 302–303ns。扣除同偏移
单核基线后，其串行比例为 -0.068–0.006，因而这是地址相关的固定延时台阶和测量波动，不是第二个
atomic 又排了一个 `B≈170ns`。

本用例对每个 64B 偏移都单独采集 AIC/AIV 单核基线，目的就是避免这种误判。

## 用例设计与校验

- 固定 DIE0 Core → GM0，基址按 512B 对齐，扫描范围不跨所选 2MiB 候选页；
- 双 Core 扫描 `0..4096B`，步长 64B，覆盖 C+C、V+V、C+V；
- 相邻 64B 地址对在首个 512B 区间内逐 64B 改变起点，并为每个相位测同址对照；
- 多 Core 覆盖同址及 `64/128/256/512/1024/2048/4096B` 步长；
- 两组热点覆盖同址、64B 同 128B、64B 跨 128B，以及 `128/512/1024B` 间距；
- 纯 AIC/AIV 近半分组；混合场景按 AIC/AIV 分组，确保不是按交错的 worker 编号误分组；
- 每个 launch 使用 4 个预热 wave、64 个计量 wave，共做 10 个轮换顺序的 sweep；
- 所有 Core 使用同一个未来 SYS_CNT 截止点，计时区间内只有一次 `atomicAdd`；
- host 校验完整目标内存和每个 wave 的 atomic 返回值；两组地址分别验证各自独立的连续旧值序列。

完整设备结果见 [results/atomic_bank_conflict/report.md](results/atomic_bank_conflict/report.md)，原始证据、JSON
汇总和 SVG 曲线位于同一目录。
